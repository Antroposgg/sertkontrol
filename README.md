# Сертконтроль

> Разделы следуют чек-листу «Формат сдачи» кейса (КЕЙС §4).
> **Все данные реестра в текущей версии — ТЕСТОВЫЕ (демо-снапшот), а не официальный источник.**

## Назначение

Бот и мини-приложение в MAX для импортёров и селлеров: проверить сертификат или декларацию о соответствии
по номеру или PDF-выписке, поставить документ на контроль и получить уведомление, когда его статус в реестре изменится.

## Основной пользовательский сценарий

1. Переслать боту выписку (PDF) или номер документа.
2. Получить карточку вердикта: статус, сроки, заявитель, продукция, дата данных; каждая строка помечена «факт / расчёт / рекомендация».
3. Нажать «На контроль».
4. Нажать «Симулировать обновление» (демо-режим).
5. Получить уведомление о смене статуса.

Статус реализации — [`docs/plan.md`](docs/plan.md). Все пять шагов работают на демо-данных (N → N+1);
уведомление приходит в чат MAX ровно одно на документ и версию данных. Номер с 1–2 ошибками распознавания или
опечатками находится нечётким поиском и подтверждается вопросом «Это номер …?».

## Состав и архитектура

| Компонент | Что делает |
|---|---|
| `certd` (C++20, Drogon) | Webhook бота, REST API мини-приложения, распознавание, вердикт, уведомления о смене статуса (очередь задач + outbox с лимитами MAX), раздача мини-приложения |
| `ingest` (C++20) | Раз в сутки собирает неизменяемый снапшот реестра, считает diff, сообщает `certd` о новой версии (`NOTIFY`); `--demo` — демо-пара N/N+1 |
| PostgreSQL 16 | Пользователи, портфель, очереди и outbox |
| `web/` (React + TS) | Мини-приложение MAX |
| Caddy (профиль `prod`) | TLS для webhook и мини-приложения на VPS |

Подробно — [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md), решения — [`docs/adr/`](docs/adr/README.md), карта кода — [`CLAUDE.md`](CLAUDE.md).

## Запуск одной командой

```bash
docker compose up --build
```

Проверка: `curl http://localhost:8080/healthz` → `{"status":"ok","db":"ok","snapshot_version":1}`; мини-приложение — http://localhost:8080/.
Файл `.env` для локального запуска не обязателен: без токена бота мини-приложение в браузере работает от тестового
пользователя `1000001` ([ADR-0013](docs/adr/0013-dev-auth-without-max.md)).

## Параметры и переменные окружения

Шаблон — [`.env.example`](.env.example) (все значения пустые; рабочие токены в репозиторий не кладутся).

| `MAX_BOT_USERNAME` | — | Публичное имя бота — для кнопок, открывающих мини-приложение |

| `CERTD_RECOG_THREADS`, `CERTD_RECOG_QUEUE` | `2`, `8` | Пул распознавания PDF и его очередь |
| `POSTGRES_DB`, `POSTGRES_USER` | `sertkontrol` | База и пользователь |
| `POSTGRES_PASSWORD` | пусто | Пусто — локальный режим без пароля во внутренней сети compose ([ADR-0009](docs/adr/0009-local-run-without-secrets.md)); на VPS обязателен |

| `CERTD_PUBLISH_PORT` | `8080` | Порт certd на хосте |

| `APT_MIRROR` | `http://mirror.yandex.ru/ubuntu` | Зеркало apt при сборке образа ([ADR-0011](docs/adr/0011-apt-mirror-build-arg.md)) |

## Зависимости

- C++: только пакеты Ubuntu 24.04 — [`docker/apt-build-deps.txt`](docker/apt-build-deps.txt), [`docker/apt-runtime-deps.txt`](docker/apt-runtime-deps.txt).
- Web: [`web/package-lock.json`](web/package-lock.json), Node.js 24 ([ADR-0007](docs/adr/0007-node-24-lts.md)).
- Образы: `ubuntu:24.04`, `node:24-slim`, `postgres:16`, `caddy:2`.

## Внешние сервисы и интеграции

- **MAX Bot API** (`https://platform-api2.max.ru`) — бот: webhook, отправка сообщений, ответы на кнопки, скачивание вложений.
  Сертификат API выпущен УЦ Минцифры; его корень встроен в образ ([ADR-0012](docs/adr/0012-mintsifry-root-ca.md)).
  Webhook MAX принимает только HTTPS на 443 — нужен VPS с доменом и профиль `prod` (Caddy).
- **MAX Bridge** (`https://st.max.ru/js/max-web-app.js`) и **MAX UI** (`@maxhub/max-ui`, MIT) — мини-приложение.
- REST API мини-приложения описан в [`openapi.yaml`](openapi.yaml).
- **Реестры Росаккредитации (открытые данные ФСА)** — не подключены: свежесть и формат наборов не подтверждены. Используются тестовые данные (см. ниже).

## Работа с данными

- Реестр хранится в неизменяемом бинарном снапшоте, `certd` отображает его в память ([ADR-0001](docs/adr/0001-registry-in-mmap-snapshot.md)).
- В PostgreSQL — только пользовательские данные: портфель, ИНН поставщиков, очереди. Файлы пользователей не сохраняются.
- Схема — [`db/migrations/`](db/README.md), применяется сервисом `migrate` при старте.

## Тестовые данные

**Все данные реестра — вымышленные демо-записи** (`data/demo/`): наименования «ТЕСТОВЫЙ …», ИНН с верной контрольной цифрой, но не реальные.
Два набора: `base.tsv` — снапшот N (данные на 25.09.2026), `next.tsv` — N+1 (26.09.2026) с пятью изменениями,
в том числе приостановкой декларации 89369/26; таблица изменений — [`data/demo/README.md`](data/demo/README.md).
Мини-приложение постоянно показывает пометку «Тестовые данные».

## Пошаговый сценарий проверки и ожидаемое поведение

**Локально, без MAX:**
1. `docker compose up --build` → `migrate` и `ingest-demo` завершаются с кодом 0 (`ingest-demo` пишет «снапшот N v1 …; N+1 v2 …;
   изменений N → N+1: 5 … ТЕСТОВЫЕ ДАННЫЕ»); `ingest` остаётся работать и ждёт ежедневного запуска в 04:00 МСК.
2. `curl http://localhost:8080/healthz` → `200`, `"snapshot_version":1`.
3. Открыть http://localhost:8080/ → экран согласия на обработку данных → «Согласен» (один раз; до согласия
   REST отвечает `403 consent_required`, как и бот не обрабатывает сообщения без согласия) → вкладка «Добавить» → ввести `ЕАЭС N RU Д-CR.РА08.В.89369/26` → «Проверить».
   Ожидается карточка «✅ Декларация RU Д-CR.PA08.B.89369/26 — действует» с блоками «Факт / Расчёт / Рекомендация»,
   «Данные реестра на 25.09.2026» и пометкой «Тестовые данные».
4. «На контроль» → вкладка «Портфель» → документ в списке; фильтр «прекращён» → пусто; «Снять» → список пуст.
5. Номер `ЕАЭС N RU Д-CR.РА07.В.89369/26` → «Нет в данных реестра», подсказка «мог быть зарегистрирован после 25.09.2026» и похожие номера серии 89369/26.
   Номер `RU Д-CR.PA08.B.B9369/26` (буква B вместо цифры 8 — типичная ошибка распознавания) → «Похоже на номер
   RU Д-CR.PA08.B.89369/26 …» и кнопка «Да, проверить» → карточка найденного документа.
   Другие номера с ожидаемыми вердиктами — [`data/demo/README.md`](data/demo/README.md).
6. Снова поставить 89369/26 на контроль → вкладка «Данные» → «Симулировать обновление».
   Ожидается «Изменилось документов в портфеле: 1», дата данных 26.09.2026 и версия 2; в «Портфеле» статус «приостановлен»;
   «Открыть» → экран «Документ»: «26.09.2026 — действует → приостановлен с 26.09.2026». Без токена бота сообщение в чат не
   отправляется, но уведомление фиксируется (повторное нажатие даёт «не изменились»).
7. «Сбросить демо» → данные снова на 25.09.2026, статус «действует» — сценарий можно пройти заново.
8. Через API (описание — [`openapi.yaml`](openapi.yaml)): `curl -X POST http://localhost:8080/api/v1/me/consent` → `204`
   (без этого шага — `403 consent_required`), затем
   `curl "http://localhost:8080/api/v1/check?number=RU%20D-CR.PA08.B.89369/26"` → JSON с `"level":"ok"`,
   `curl -X POST http://localhost:8080/api/v1/demo/simulate-update` → `{"notified":…}`.

**В MAX (нужны токен, секрет и HTTPS-домен):**
1. Открыть бота → «Согласен».
2. Отправить номер или переслать PDF-выписку → «⏳ Проверяю документ…» → карточка вердикта.
   Номер с ошибкой (`RU Д-CR.PA08.B.B9369/26`) → «Это номер RU Д-CR.PA08.B.89369/26?» `[Да] [Нет]` → «Да» → карточка.
   «Подробнее» под карточкой открывает мини-приложение сразу на экране «Документ».
3. «На контроль» → «🔔 … на контроле» с кнопкой «Снять с контроля».
4. Отправить 4 и более номеров → сводка и «Поставить все на контроль».
5. «Указать поставщика» под карточкой → прислать ИНН (например, `7700000016`) → «… на контроле, поставщик — ИНН …».
6. Мини-приложение → «Данные» → «Симулировать обновление» → в чат приходит одно сообщение
   «Декларация … — **приостановлен** до 26.12.2026 (было: действует) … Данные реестра на 26.09.2026».

## Известные ограничения

- Данные ФСА не подключены — работа на демо-данных (свежесть и формат открытых наборов не подтверждены).
- Боевой источник не подключён, поэтому ежедневный запуск `ingest` пока ничего не собирает (пишет, что источник не подтверждён);
  поток «новая версия → уведомления» проверен на демо-паре и тестами. Фото, OCR, сканер QR камерой и импорт CSV —
  этап 4; фото сейчас получают ответ «пришлите PDF».
- Нечёткий поиск исправляет ошибки в серии и номере (до 2 правок, путаница O/0, B/8, S/5, I/1, Z/2); при двух
  одинаково близких кандидатах вопрос не задаётся — показываются похожие номера ([`docs/rules.md`](docs/rules.md)).
- Скачивание вложений MAX по `payload.url`: нужна ли авторизация и сколько живёт ссылка, в документации MAX не сказано —
  реализовано без токена, проверяется вручную в MAX.
- Без `MAX_BOT_TOKEN` сервер — однопользовательский локальный стенд; не публикуйте порт 8080 в интернет без токена.
- REST `/api/v1` — внутренний API мини-приложения (OpenAPI 3.1, [`openapi.yaml`](openapi.yaml), проверен линтером
  и контрактными тестами schemathesis). Считается ли он «собственным API» кейса — открытый вопрос к организаторам
  (АРХ §11); `DATA-API.yaml` не подготовлен. Авторизация — подписанная MAX `initData`, отдельных учётных записей нет.
- На метод `TRACE` сервер отвечает 405 без заголовка `Allow` — ограничение Drogon 1.8.7
  ([ADR-0016](docs/adr/0016-trace-405-without-allow.md)); на остальные неподдерживаемые методы — 405 с `Allow`.
- Исходящие сообщения MAX — at-least-once: ключа идемпотентности в документации MAX API не найдено (АРХ §7.5).
- Исходящие сообщения идут не быстрее лимитов MAX (30 запросов/с, 2 сообщения/с в чат, АРХ §7.6); при 429 отправитель
  делает паузу и повторяет, поэтому длинная рассылка уведомлений растягивается во времени.

## Развёртывание на VPS

1. VPS в РФ, Docker, домен с A-записью на сервер; во входящем файрволе открыты **80 и 443** (Caddy получает
   сертификат Let's Encrypt и принимает webhook MAX только на 443).
2. `.env` рядом с `compose.yaml`: `SK_DOMAIN`, `MAX_BOT_TOKEN`, `MAX_WEBHOOK_SECRET`, `MAX_BOT_USERNAME`,
   `POSTGRES_PASSWORD`, `POSTGRES_HOST_AUTH_METHOD=scram-sha-256`.
3. Запуск: `docker compose --profile prod up -d --build`; проверка — `https://<домен>/healthz` → 200.
   Бот работает внутри контейнера `certd`: webhook `/max/webhook`, обработка событий, отправка сообщений.
4. **Подписка webhook — один раз после первого запуска** (без неё MAX не шлёт боту события). Команда выполняется
   внутри `certd`: там токен и корень Минцифры, без которого TLS к API MAX не проверится:

   ```bash
   docker compose --profile prod exec certd sh -c 'curl -s -X POST -H "Authorization: $MAX_BOT_TOKEN" -H "Content-Type: application/json" -d "{\"url\":\"https://$SK_DOMAIN/max/webhook\",\"update_types\":[\"bot_started\",\"message_created\",\"message_callback\"],\"secret\":\"$MAX_WEBHOOK_SECRET\"}" https://platform-api2.max.ru/subscriptions'
   ```

   Ожидается `{"success":true}`; список подписок — `GET https://platform-api2.max.ru/subscriptions` тем же способом.
5. В настройках бота на платформе MAX указать адрес мини-приложения `https://<домен>/`.
6. Лог: `docker compose --profile prod logs -f certd`. Ошибки отправки видны как `outbox N не отправлено: …`.

**Чем проверить.** Отправьте боту номер из демо-данных, например `ЕАЭС N RU Д-CR.РА08.В.89369/26`
(остальные номера и ожидаемые вердикты — [`data/demo/README.md`](data/demo/README.md)), или перешлите PDF
[`tests/fixtures/pdf/extract-89369-26.pdf`](tests/fixtures/pdf/extract-89369-26.pdf) — тестовая выписка с номером в
тексте и QR со ссылкой на реестр.

## Ручная проверка в MAX (чек-лист)

- [ ] Webhook: `POST /subscriptions` с `url=https://<домен>/max/webhook`, `secret=<MAX_WEBHOOK_SECRET>`; событие доходит, ответ 200.
- [ ] Скачивание PDF-вложения по `payload.url` без токена работает.
- [ ] Кнопки `callback`, `link`, `open_app` (с `MAX_BOT_USERNAME`) отображаются и срабатывают в мобильном и веб-клиенте.
- [ ] Мини-приложение открывается из бота, `X-Max-Init-Data` проходит проверку подписи; экран согласия показывается один раз.
- [ ] «Подробнее» под карточкой открывает «Документ» с номером (`start_param`).
- [ ] Номер с ошибкой → «Это номер …?» → «Да» → карточка; «Нет» → просьба прислать номер ещё раз.
- [ ] HTML-разметка карточки (`<b>`) отображается.
- [ ] «Симулировать обновление» → уведомление в чате приходит одно, в пределах нескольких секунд.

## Остановка и повторный запуск

```bash
docker compose down        # остановить, данные сохраняются в томах
docker compose up -d       # запустить снова
docker compose down -v     # остановить и удалить данные (полный сброс)
```

## Разработка

Проверки в CI (те же скрипты — локально, [`scripts/gate.sh`](scripts/gate.sh) запускает все):
сборка GCC 13 и clang 18 с `-Werror`, тесты дважды, ASan/UBSan и ThreadSanitizer, покрытие ≥ 70% (C++ и web),
clang-tidy, ESLint, tsc strict, fuzz-цели libFuzzer (smoke 60 с на цель, [`fuzz/`](fuzz/README.md)),
бенчмарки против целей АРХ §2 ([`bench/`](bench/README.md): на 1 млн записей точный поиск p99 ≈ 3 мкс,
нечёткий ≈ 0,3 мс при целях 1 и 5 мс), линтер OpenAPI и контрактные тесты schemathesis на живом стеке,
`docker build --no-cache` с таймером, gitleaks.

Команды сборки, тестов и проверок — [`CLAUDE.md`](CLAUDE.md#команды). Лицензия — [GPL-3.0-or-later](LICENSE).
