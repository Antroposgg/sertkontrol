# Формат снапшота v1 (контракт C2)

Снапшот — неизменяемый файл `snap-<version>.bin`. Его пишет `ingest` (`libs/snapshot/src/writer.cpp`),
а `certd` отображает в память (`libs/snapshot/src/reader.cpp`). Раскладка описана в коде в
[`libs/snapshot/include/sertkontrol/snapshot/format.hpp`](../libs/snapshot/include/sertkontrol/snapshot/format.hpp)
и совпадает с этим документом. Обоснование выбора — [ADR-0001](adr/0001-registry-in-mmap-snapshot.md), АРХ §6.

## Общие правила

- Порядок байтов — little-endian (`static_assert(std::endian::native == std::endian::little)`).
- Каждая секция начинается со смещения, кратного 64 байтам; промежутки заполнены нулями.
- Одинаковый вход writer-а даёт побайтно одинаковый файл: порядок записей и таблица строк детерминированы.
- Запись атомарна: `snap-<v>.bin.tmp` → `fsync` → `rename` → `fsync` каталога.

## Заголовок — 256 байт

| Смещение | Тип | Поле | Значение |
|---|---|---|---|
| 0 | `char[8]` | `magic` | `SKSNAP01` |
| 8 | `u32` | `format_version` | `1` |
| 12 | `u32` | `canon_version` | `canon::kVersion`, с которой посчитаны ключи |
| 16 | `u64` | `snapshot_version` | = `snapshot_version.version` в PostgreSQL (C8) |
| 24 | `i32` | `source_date` | дата актуальности данных, дни от 1970-01-01 |
| 28 | `u32` | `flags` | бит 0 — демо-данные |
| 32 | `u64` | `record_count` | N |
| 40 | `u64` | `string_count` | M (строка 0 — пустая) |
| 48 | `char[32]` | `source` | идентификатор источника, дополнен нулями (≤ 31 байта) |
| 80 | `{u64 offset, u64 size}[8]` | `sections` | таблица секций, индексы — ниже |
| 208 | `u64` | `payload_xxh3` | XXH3-64 (seed 0) всех байтов файла после заголовка |
| 216 | `u8[40]` | `reserved` | нули |

## Секции

| № | Секция | Содержимое | Байт на элемент |
|---|---|---|---|
| 0 | `keys` | `u64[N]` — `canon::key_hash` номера, по возрастанию | 8 |
| 1 | `records` | `PackedRecord[N]`, `records[i]` соответствует `keys[i]` | 64 |
| 2 | `serial_index` | `{u64 key, u32 index}` без выравнивания, по возрастанию `(key, index)`; `key = серия × 100 + ГГ` | 12 |
| 3 | `string_offsets` | `u64[M+1]`: строка `i` — байты `[offsets[i], offsets[i+1])` секции 4 | 8 |
| 4 | `string_data` | UTF-8 без разделителей | — |
| 5 | `lab_index` | зарезервировано для графа риска (F11); в v1 пусто | — |
| 6–7 | — | зарезервировано | — |

Записи упорядочены по `(key, каноническая строка)`, поэтому номера с одинаковым хэшем стоят рядом,
и поиск проверяет весь `equal_range` (АРХ §7.2). Тот же порядок использует diff (АРХ §7.3, этап 2).
В `serial_index` попадают только номера, которые разбирает грамматика (`canon::parse`); старые форматы без
года в индекс не входят, но точным поиском находятся.

## `PackedRecord` — 64 байта

| Смещение | Тип | Поле |
|---|---|---|
| 0 | `u8` | `status` (`snapshot::Status`) |
| 1 | `u8` | `kind` (`canon::DocKind`) |
| 2 | `u8` | `flags` (0) |
| 3 | `u8` | резерв |
| 4 | `i32` ×4 | `issue_date`, `expiry_date`, `status_date`, `suspended_until`; `INT32_MIN` — нет даты |
| 20 | `u32` ×8 | ссылки в таблицу строк: `number`, `applicant_name`, `applicant_inn`, `manufacturer_name`, `product`, `tnved`, `country`, `lab_accreditation` |
| 52 | `u32` | резерв |
| 56 | `u64` | `registry_id` — ID записи в реестре ФСА |

Одинаковые строки (наименования заявителей, коды ТН ВЭД) хранятся один раз. `product` обрезается до 128 байт
по границе символа UTF-8.

## Что проверяет ридер при открытии

Файл считается недоверенным. `open_snapshot` возвращает `kSnapshotUnavailable`, если:

1. файл короче заголовка, `magic` или `format_version` не совпадают;
2. `canon_version ≠ canon::kVersion` — ключи посчитаны по другим правилам (АРХ §7.1);
3. любая непустая секция не выровнена или выходит за файл (проверка без переполнения);
4. размеры секций не согласованы с N и M;
5. не совпадает `payload_xxh3`;
6. смещения строк не начинаются с 0, убывают или не заканчиваются размером `string_data`;
7. ключи не отсортированы; запись ссылается на строку ≥ M; `status` или `kind` вне перечисления;
8. `serial_index` не отсортирован или ссылается на запись ≥ N.

После успешного открытия доступ к данным не требует проверок. Проверка — O(размер файла): для демо —
микросекунды; для полного набора (≈ 2–5 ГБ) — порядка секунды и прогрев страниц. Если это станет узким
местом рестарта (цель ≤ 5 с, АРХ §2), проверку ссылок можно вынести в `ingest` и оставить в ридере только XXH3.

## Время жизни объектов

- `PackedRecord`, элементы `serial_index` и смещения строк читаются через `std::memcpy` в локальную
  переменную. `mmap` не входит в перечень операций, неявно создающих объекты в C++20 (P0593R6), а
  `std::start_lifetime_as` есть только в C++23 (АРХ §7.4).
- `keys` отдаются как `std::span<const uint64_t>` прямо в отображение: двоичный поиск по плотному массиву —
  основа производительности точного поиска (АРХ §6, §7.2), а контракт C2 фиксирует `keys()` как `span`.
  `uint64_t` — тип с неявным временем жизни; P0593 прямо допускает, что реализации относят `mmap` к операциям,
  создающим такие объекты, и GCC/clang на Linux ведут себя именно так. Это единственное место, где формат
  опирается на поведение реализации; при переходе на C++23 — заменить на `std::start_lifetime_as_array`.
- `RecordView` содержит `string_view` в отображение и валиден, пока жив `SnapshotPtr`. `munmap` — в деструкторе
  последнего владельца (`SnapshotHolder`, АРХ §7.4).

## Ограничения v1

- Writer держит все записи в памяти. Для демо-данных этого достаточно; потоковая сборка через временный файл и
  сортировку перестановки `(key, idx)` (АРХ §6, 12 байт на запись) — вместе с адаптером открытого набора ФСА.
- `lab_index` не заполняется (граф риска F11 — Could).

## Изменение формата

Любое изменение раскладки — новый `kFormatVersion`, обновление этого документа, `format.hpp`, тестов
`tests/snapshot/` и запись в [`changelog-contracts.md`](changelog-contracts.md). Ридер открывает только свою версию.
