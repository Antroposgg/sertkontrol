# Требования хакатона MAX, трек «Эффективный бизнес»

> Источник: «Эффективный бизнес.pdf» (Минобрнауки России × MAX), конвертирован из PDF в Markdown.

---

## 1. Постановка задачи

Разработать чат-бота или мини-приложение на Платформе для бизнеса в MAX. Продукт должен решать актуальную задачу бизнеса и иметь практическую ценность для целевой аудитории.

Направление Сертконтроля в треке — «Импорт, экспорт и промышленная кооперация»: работа с требованиями, документами, поставщиками, сертификацией. Смежное — «Цифровое сопровождение документов и разрешений»: проверка и отслеживание сертификатов и статусов.

### Онлайн-этап — разработка MVP

1. Определить целевую аудиторию и приоритетный пользовательский сегмент, обосновать выбор.
2. Определить конкретную проблему пользователя и подтвердить её актуальность.
3. Продумать UX и основной сценарий: как пользователь начинает работу, какие действия совершает, какой результат получает.
4. **Создать MVP — чат-бота или мини-приложение в MAX — с выданным токеном.**
5. Определить потенциал масштабирования и условия внедрения и развития.
6. Определить ожидаемый эффект: какую часть процесса продукт улучшает и по каким показателям это проверить.
7. Подготовить презентацию проекта, пройти отбор в финал.

### Офлайн-этап — защита перед жюри

1. Проработать сценарий пилотного запуска и внедрения.
2. Доработать решение, подготовить демонстрацию и выступление.
3. Защитить проект очно **29 октября в Казани**. В каждом направлении — три команды-призёра.

## 2. Ограничения (обязательны)

1. Решение соответствует тематике трека и решает обозначенную командой задачу бизнеса. Актуальность обоснована.
2. MAX используется как среда реализации и/или взаимодействия. **Основной пользовательский сценарий должен быть доступен для проверки в MAX.**
3. Можно разрабатывать под мобильную или веб-версию MAX, но **функциональность должна быть доступна в обеих версиях**.
4. Для MAX рекомендуются JavaScript и React. Другие языки и API допустимы.
5. Форма решения:
   - чат-бот;
   - или чат-бот с подключённым мини-приложением.
   Мини-приложение подключается к чат-боту и не используется изолированно от него.
6. Собственный API не обязателен и сам по себе баллов не даёт.
7. **Запрещены** закрытые библиотеки, частные API и чужой код без разрешения на свободное распространение и использование.
8. **Нельзя размещать в репозитории рабочие токены, пароли, API-ключи и другие секреты.**
9. Соблюдаются законодательство РФ, актуальные правила платформы MAX и правила хакатона.
10. **Если вместо реального подключения к внешней системе используются тестовые, заранее подготовленные или смоделированные данные, это явно указывается в материалах.**
11. Ник чат-бота после создания изменить нельзя.
12. **После дедлайна переданная версия исходного кода не изменяется.**

---

## 3. Рекомендации организаторов

1. Не брать слишком широкую аудиторию. Нужен конкретный пользователь и сегмент: отрасль, регион, масштаб, этап развития, ситуация.
2. Подтвердить проблему: открытыми данными, исследованиями, официальными источниками, наблюдениями, интервью или аргументированными допущениями. Отделять факты от гипотез.
3. Сфокусироваться на одном приоритетном сценарии и реализовать его от начала до конца.
4. Сначала пользовательская задача, потом технология. Бот, мини-приложение, LLM — инструменты, а не самоцель.
5. Учитывать источник данных. Если реальная интеграция недоступна, можно брать тестовые данные, но с явной пометкой.
6. Масштабирование — это возможность перенести решение в другой контекст, а не число потенциальных пользователей. Нужно показать, что остаётся неизменным, а что адаптируется.

## 4. Формат сдачи

### Обязательно для всех решений

**1. Работающее решение в MAX.** Ссылка или иной способ доступа к боту или мини-приложению для прохождения основного сценария.

**2. Зафиксированная версия исходного кода.**

- Это git-репозиторий с commit hash или архив с контрольной суммой.
- После дедлайна версия не меняется.
- Изменять код и презентацию смогут только финалисты после объявления результатов онлайн-этапа.

**3. `README.md` содержит:**

- [ ] назначение решения;
- [ ] основной пользовательский сценарий;
- [ ] состав и архитектуру решения;
- [ ] **одну команду для запуска всех локальных компонентов через Docker**;
- [ ] необходимые параметры окружения;
- [ ] переменные окружения;
- [ ] используемые порты;
- [ ] зависимости;
- [ ] внешние сервисы и интеграции;
- [ ] описание работы с данными;
- [ ] порядок работы с тестовыми данными;
- [ ] пошаговый сценарий проверки;
- [ ] примеры ожидаемого поведения системы;
- [ ] известные ограничения;
- [ ] порядок остановки и повторного запуска.

Если для MVP нужен внешний сервис, который невозможно воспроизвести в Docker, отдельно указать его назначение и условия проверки.

Контейнеризация не заменяет работающую версию в MAX: бот или мини-приложение должны оставаться доступны для прохождения основного сценария.

**4. Файл зависимостей.** Например, `requirements.txt`, `package-lock.json` или другой файл, фиксирующий библиотеки и версии.

**5. Docker-конфигурация.** Решение готово к воспроизводимому запуску в Docker. В репозитории лежат:

- [ ] `Dockerfile` для компонентов, запускаемых локально;
- [ ] `compose.yaml` или `docker-compose.yml`, который запускает все локальные компоненты **одной командой**;
- [ ] `.dockerignore`;
- [ ] `.env.example` без рабочих токенов, паролей и ключей.

Готовый образ в Docker Hub допустим как дополнение, но не заменяет файлы для воспроизводимой сборки из исходников.

**Сборка в Docker — не более 5 минут** (без учёта первоначальной загрузки базовых образов). Docker-конфигурация содержит только необходимые компоненты и зависимости, без избыточных операций, заметно увеличивающих время сборки.

**6. Презентация в PDF.**

Первый слайд служебный, он не оценивается. На нём:

- ссылка на бота или мини-приложение в MAX;
- ссылка на Git-репозиторий и commit hash;
- адрес собственного API, если он используется;
- тестовые логины и пароли;
- рабочие токены, API-ключи и значения переменных окружения, нужные для запуска и проверки;
- краткий порядок прохождения основного сценария.

Со второго слайда рекомендуется раскрыть:

- название и состав команды;
- executive summary;
- ЦА, проблему и её актуальность;
- решение и основной сценарий;
- ожидаемый эффект;
- архитектуру;
- данные и интеграции;
- масштабирование и условия адаптации;
- ограничения, риски и допущения;
- источники.

### Только для решений с собственным API

> Открытый вопрос из `ARCHITECTURE.md` §11: считается ли `/api/v1` мини-приложения «собственным API». Если да — нужно всё ниже.

1. Адрес проверяемого API: полный HTTPS-адрес, доступный весь период проверки.
2. OpenAPI 3.0 или 3.1 — `openapi.yaml` или `openapi.json` с методами и форматами.
3. Тестовые учётные записи для ролей, нужных в обязательных сценариях. Административный доступ — только при необходимости.
4. Тестовые данные: JSON, CSV или иной согласованный формат для воспроизводимой проверки.
5. `DATA-API.yaml`, содержащий:
   1. версию конфигурации — версию схемы файла, по которой платформа оценки выполняет проверку;
   2. наименование решения или идентификатор команды;
   3. базовый адрес API — единый HTTPS-адрес, относительно которого формируются запросы;
   4. перечень обязательных проверок — методы основной функциональности;
   5. HTTP-метод (GET, POST, PUT, PATCH, DELETE) и относительный путь эндпоинта;
   6. параметры запроса: query, path, заголовки, тело;
   7. роль пользователя — тестовую учётку, нужную для проверки;
   8. ожидаемые статус-коды;
   9. ожидаемый формат ответа: тип содержимого, JSON-структуру, обязательные поля.

## 5. Критерии оценки

Каждый критерий оценивается по шкале 0–3:

| Балл | Значение |
|---|---|
| 0 | Не выполнен или решение невозможно оценить |
| 1 | Слабо, есть существенные пробелы |
| 2 | Частично: в основном выполнен, есть заметные недочёты |
| 3 | Хорошо: выполнен полно и качественно |

### 5.1. Допуск

Решение получает 0 баллов и дальше не оценивается, если:

1. оно не по теме: решает другую задачу или не использует MAX как среду реализации или взаимодействия;
2. **бот или мини-приложение в MAX не запускается, не отвечает или основной сценарий невозможно проверить**;
3. нет презентации.

### 5.2. Онлайн-этап — продуктовая оценка (40% балла)

| Критерий | Вес | Что проверяют |
|---|---|---|
| Потенциал масштабирования | 35% | Конкретные контексты, регионы, организации помимо исходного кейса; направления соответствуют логике продукта; условия адаптации (данные, интеграции, ресурсы, изменения); ограничения и риски; реалистичный порядок тиражирования |
| Пользовательская ценность | 25% | Чёткая ЦА и сегмент; конкретная актуальная потребность; полезный результат; преимущество перед текущим способом; востребованность подтверждена данными, наблюдениями или допущениями |
| UX/UI и удобство | 20% | Путь соответствует приоритетному сценарию; последовательность понятна без пояснений; ключевые действия легко найти; **интерфейс сообщает о загрузке, результате и ошибке**; нет лишних шагов, тупиков и противоречивых переходов |
| Обоснованность и целостность | 15% | Соответствие задаче; связь «проблема → механика → результат»; аргументированные решения и допущения; функции образуют единый продукт; реалистичность в заданных условиях |
| Качество презентации | 5% | Структура, ясность, достаточность, читаемые схемы, нет перегруза |

### 5.3. Онлайн-этап — техническая оценка (60% балла)

| Критерий | Вес | Что проверяют |
|---|---|---|
| Работоспособность и полнота основных функций | 30% | Основной сценарий проходится полностью; ключевые функции работают; для собственного API обязательные проверки проходят |
| Корректность интеграции и обмена данными | 20% | Компоненты взаимодействуют корректно и последовательно; данные и состояния обрабатываются предсказуемо; внешние интеграции работают по заявленной логике; для API статус-коды, форматы, заголовки и обязательные поля соответствуют контракту |
| Техническая реализация и архитектура | 20% | Структура логична и соответствует масштабу MVP; понятны компоненты, роли и связи; логика разделена так, чтобы решение можно было поддерживать и развивать; технические решения соответствуют функциональности |
| Стабильность и обработка ошибок | 10% | Стабильно при повторном прохождении сценария; ошибки и некорректные действия обрабатываются предусмотренным образом; после ошибки можно продолжить без перезапуска; нет систематических сбоев, тайм-аутов и критичных задержек |
| Безопасность, зависимости, работа с данными | 10% | **Секретов нет в коде**; зависимости и версии зафиксированы; доступ к данным соответствует логике; данные и внешние сервисы описаны; нет очевидных критичных рисков |
| Техническая документация и комплектность | 10% | Материалы соответствуют зафиксированной версии; **решение воспроизводится по инструкции**; описаны запуск, архитектура, зависимости, окружение, интеграции; указан порядок проверки и ожидаемый результат; **известные ограничения зафиксированы** |

### 5.4. Платформенный бонус — +0,15 балла

Бонус начисляется только целиком: 0 или 0,15. Условия:

- основной сценарий полностью работает и доступен для проверки;
- использована возможность MAX сверх минимальных требований;
- эта возможность создаёт ценность, органично встроена, работает от начала до результата и описана в материалах.

Собственный API, число функций или базовые обязательные возможности сами по себе не основание для бонуса.

> В Сертконтроле бонус целится через F10 — сканирование QR камерой через `openCodeReader`.

### 5.5. Финал

Итог финала складывается так:

- 40% — техническая оценка продукта;
- 60% — оценка защиты.

Платформенный бонус в финал не переносится.

| Критерий | Вес |
|---|---|
| Пользовательская ценность и соответствие задаче | 25% |
| Потенциал масштабирования и тиражирования | 25% |
| Качество MVP и пользовательского опыта | 20% |
| Сценарий запуска и внедрения | 15% |
| Качество защиты и ответов на вопросы | 10% |
| Командное владение решением | 5% |

Изменения в продукте после онлайн-этапа нужно явно отразить в финальной презентации и показать на защите.

## 6. Платформа MAX

MAX позволяет создавать чат-ботов и подключать к ним мини-приложения. Для разработки доступны:

- **API чат-ботов** — для программной реализации сценариев;
- **конструкторы сценариев ботов** — без программирования;
- **MAX Bridge** — библиотека для взаимодействия мини-приложения с API MAX и API устройства. Даёт информацию о платформе запуска (iOS, Android, desktop, web) для адаптации поведения;
- **MAX UI** — React-компоненты для интерфейсов мини-приложений в стилистике MAX.

Мини-приложения работают на стандартных веб-технологиях (HTML, JavaScript, CSS). **Для подключения к MAX мини-приложение должно работать по HTTPS.**

Чат-бот подходит, если пользователь:

- отвечает на несколько последовательных вопросов;
- выбирает из небольшого числа опций;
- получает персональный результат или рекомендацию;
- проверяет статус;
- получает уведомление или напоминание;
- регулярно выполняет короткое действие.

Мини-приложение оправдано, если пользователю нужно:

- заполнить сложную форму;
- работать с большим числом параметров;
- сравнивать объекты;
- работать со списком или каталогом;
- возвращаться к ранее введённым данным;
- видеть несколько связанных элементов сразу;
- работать со сложным визуальным интерфейсом.

> **Документация MAX развивается и обновляется. Перед началом разработки и перед сдачей обязательно сверяйтесь с актуальной документацией и историей изменений API, а не со старыми примерами и сторонними инструкциями.**

Токен чат-бота предоставляют организаторы.

## 7. Работа с официальными данными

1. **Использовать первоисточник.** Официальный источник приоритетнее пересказов и сторонних статей.
2. **Проверять актуальность и применимость.** Правила, справочники и показатели меняются и зависят от территории, периода и категории пользователя. Если актуальность влияет на результат, продумать:
   - когда данные обновлены;
   - к какому периоду и территории они относятся;
   - как часто их нужно обновлять;
   - как пользователь узнает источник и дату актуальности.
3. **Разделять факты, расчёты и рекомендации.** Пользователь должен понимать происхождение результата. Показать:
   - что получено из официального источника;
   - что рассчитано продуктом;
   - что является рекомендацией;
   - что является допущением или модельными данными.
4. **Не имитировать интеграции.** Без доступа к реальной системе использовать тестовые, синтетические или подготовленные данные. В материалах явно указать, какие интеграции модельные и что потребуется для реальных после MVP.
5. **Учитывать ограничения генеративного ИИ.** Если LLM работает с нормативными документами или критичной информацией:
   - привязывать ответы к источникам;
   - показывать основание;
   - предусмотреть ситуацию, когда надёжного ответа нет;
   - не выдавать предположение модели за официальный факт.

> В Сертконтроле п. 3 реализован метками «факт / расчёт / рекомендация» в карточке вердикта (F3), п. 2 — датой данных в каждой карточке и в `/data-status`, п. 4 — пометкой демо-режима (F6).

## 8. Границы MVP

MVP — не уменьшенная версия большого продукта, а минимальная версия, в которой пользователь полностью получает основной результат. Приоритизация по MoSCoW:

| Категория | Смысл |
|---|---|
| **Must Have** | Функции, без которых основной сценарий не работает |
| **Should Have** | Улучшают продукт, но не обязательны для результата |
| **Could Have** | Только после готовности основного сценария |
| **Won't Have** | Сознательно не реализуются в текущей версии |

Для хакатона особенно важно определить Won't: ограничение объёма — часть сильного продуктового решения.

От проблемы к решению организаторы предлагают идти так:

1. **As Is** — как пользователь решает задачу сегодня.
2. **To Be** — что изменится на выбранном участке.
3. **Гипотеза и ожидаемый эффект.** Хотя бы один измеримый показатель: время процесса, число ручных действий, число ошибок, доля завершивших сценарий, повторные обращения, точность подбора.
4. **Границы MVP.**

## 9. Масштабирование и пилот

Масштабирование — не формулировка «запустим по всей России», а понятный путь переноса продукта из первого контекста в следующий.

| Ядро продукта (не меняется) | Переменная часть (адаптируется) |
|---|---|
| Основная пользовательская проблема | Региональные данные |
| Логика сценария | Нормативные требования |
| Архитектура | Справочники |
| Базовая модель данных | Внешние системы |
| Механика взаимодействия | Интеграции |
| Ключевые элементы интерфейса | Роли участников, бизнес-правила |

Вопросы, на которые нужно ответить:

- где ещё существует аналогичная проблема;
- куда масштабировать в первую очередь;
- что переносится без изменений;
- что потребуется адаптировать;
- какие данные, интеграции и ресурсы понадобятся;
- какие риски возникнут;
- какой следующий шаг после успешного запуска.

Пилот — первый ограниченный запуск для проверки ценности. Нужно определить:

- для кого и где проходит первый запуск;
- как продукт встраивается в существующий процесс;
- какие данные, интеграции и участники нужны;
- как пользователи получат доступ;
- по каким метрикам оценивается результат;
- какой следующий шаг после успешного пилота.
